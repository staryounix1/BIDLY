الحالة عند البدء

كانت واجهة الخدمات والطلبات في الخلفية مكتملة ومطابقة للمخطط (فئات، خدمات، حقول ديناميكية، إنشاء طلب، نشر، إلغاء). النقص الحقيقي كان في الواجهة الأمامية: لا صفحة للخدمات ولا للطلبات، ولا نموذج ديناميكي. أعدت استخدام كل ما هو موجود دون إنشاء جداول أو مسارات مكررة.

ما أُنجز في هذا الجزء

تصفّح الخدمات (جديد)

صفحة تعرض شجرة الفئات ← الفئات الفرعية ← الخدمات من قاعدة البيانات مباشرة، مع بحث، ووسوم نموذج التسعير ومتطلبات الموقع/الوجهة.

نموذج طلب ديناميكي (جديد)

يُبنى تلقائيًا من تعريفات service_fields لكل خدمة (نص، رقم، قائمة، تاريخ، منطق شرطي)، مع حقول الاستلام والوجهة عند الحاجة واختيار المدينة.

دورة حياة الطلب (مربوطة)

مسودة ← منشور عبر النشر، مع عرض الحالة في كل مرحلة. الإلغاء متاح ضمن الحالات المفتوحة فقط، والانتقالات محمية في الخادم وقاعدة البيانات.

طلباتي + التفاصيل (جديد)

قائمة بطلبات العميل وحدها، وصفحة تفاصيل تعرض الخدمة، الحالة، الأجوبة الديناميكية، الاستلام/الوجهة، الميزانية، والعروض الواردة.

تحقق المسار الحقيقي (حي)

POST /api/v1/requests (بلا رمز) → 401
POST /api/v1/requests (مزوّد) → 403 (للعملاء فقط)
POST /api/v1/requests (خدمة غير موجودة) → 404
POST /api/v1/requests (أجوبة ناقصة) → 400
POST /api/v1/requests (صحيح) → 201 · REQ-XXXXXX · DRAFT
GET  /api/v1/requests/mine → يظهر كـ DRAFT
GET  /api/v1/requests/:id (عميل آخر) → 403
POST /api/v1/requests/:id/publish → PUBLISHED
POST /api/v1/requests/:id/cancel → CANCELLED
إعادة الإلغاء/النشر → 409/422 (انتقال غير مسموح)

تحقق قاعدة البيانات

الطلب المُنشأ حُفظ فعليًا: الحالة النهائية CANCELLED، عدد صفوف الأجوبة الديناميكية 5، و published_at وcancelled_at مضبوطان، والعلاقات (العميل ← الطلب ← الخدمة ← الفئة) سليمة عبر المفاتيح الأجنبية.

اختبارات المهمة

  • إنشاء طلب صحيح
  • بيانات ناقصة/غير صحيحة
  • خدمة غير موجودة
  • ميزانية غير منطقية
  • طلب بلا مصادقة
  • وصول عميل آخر → 403
  • عرض قائمة طلباتي
  • تفاصيل الطلب للمالك
  • النشر (انتقال صحيح)
  • تعديل/نشر مكرر → رفض
  • الإلغاء ضمن الحالات المفتوحة
  • إلغاء طلب ملغى مسبقًا → رفض
